# TaskTok 商业计划书：把劳动的交易单位从“岗位”移到“可验收任务”

**这份文档回答一个问题**：当 AI Agent 可以和人一起交付工作时，工作市场的最小交易单位应该是什么。

**核心判断**：现有平台的瓶颈已从“找不到人”转移到“说不清什么算完成”。

- **需求侧失真**：一句话需求无法编译成可定价、可验收的任务，只能被包装成“岗位”按时间出售。

- **供给侧失真**：简历与关键词是弱信号，真正预测交付能力的完成率、按时率、复购率没有被沉淀。

- **平台侧缺位**：撮合可以规模化，验收不能；人机混合劳动缺少计价与责任字段。

**解法与边界**：把任务做成带 Input、Output、Acceptance 的可验收对象（TaskTok），用任务图、能力图谱、验收图谱三张网络承接。文中市场规模与单位经济均为待验证假设，需以首批真实任务校准。

# 背景：交易颗粒度正在从“岗位”继续下移到“任务”

讨论工作市场的机会，先要看清它的交易单位。**交易单位决定计价方式，计价方式决定平台能规模化到什么程度**。过去二十年，这个单位已经下移过两次，第三次正在发生。

## 三代平台把交易单位越切越细

第一代是职位市场。LinkedIn、猎聘、Boss 直聘的交易单位是“一个岗位 \+ 一段时间的人力”，计价方式是月薪，匹配对象是“人与职位”。它解决的是信息不对称，但把最大的不确定性留给了雇主：人是否交付结果，要在入职数月后才知道。

第二代是项目市场。Upwork、Braintrust、Contra 把单位切到“一个有边界的交付”，计价方式是固定价、里程碑或按小时，匹配对象仍是“人与项目”。这一步明显提高了确定性，但项目内部的拆解、验收标准与质量标准，依然由双方私下约定。Fiverr 走了另一条路：由供给方预先定义服务 SKU，把交付彻底商品化，代价是复杂工作无法被这样切分。

|平台类型|代表|交易单位|计价方式|匹配对象|未解决的环节|
|---|---|---|---|---|---|
|职位市场|LinkedIn、猎聘、Boss 直聘|岗位 \+ 时间|月薪|人与职位|结果与薪酬不挂钩|
|项目市场<br>|Upwork、Braintrust、Contra|有边界的项目|固定价、里程碑|人与项目|拆解与验收靠私下约定|
|服务商品化|Fiverr|预定义 SKU|一口价|人与服务包|复杂工作无法切分|
|任务市场（本文设想）|TaskTok|可验收任务|按结果、按里程碑、按悬赏|任务与执行单元|需自建验收与信用体系|

## 两个变量让“任务”第一次具备可交易条件

第一个变量是交付物全面数字化。市场研究、线索挖掘、数据分析、内容与代码，这些工作的产出本身就是文件、表格、数据集或仓库，可以被结构化描述、被抽样检查、被模型初审。物理世界的工作做不到这一点，所以真正的机会先出现在知识工作上。

第二个变量是执行单元不再只有人。一个人的产出正在变成“一个人 \+ 若干 Agent”的产出。这意味着市场不能再按工时定价：同一个任务，纯人工 8 小时，人机协作 45 分钟加 1\.5 小时审核，两者价格差数倍，但结果可能相同甚至更好。**当执行单元可变而计价单位不变时，按时间售卖的平台会系统性失真**。

# 痛点：撮合已经规模化，但“完成的定义”仍是空白

把三代平台放在一起看，会发现它们优化的是同一个环节：让人和需求更快地互相看见。**但工作真正的成本并不发生在“找到人”那一刻，而发生在“什么叫完成”这一判断上**。围绕这一点，需求侧、供给侧和平台侧各有一组结构性摩擦。

## 需求侧：一句话需求无法直接定价与验收

企业真实的需求几乎都以目标形式出现：“看看东南亚市场有没有机会”“把美国区投放成本压下来”。这类表述缺少三样东西：可交付的产物、可判定的完成标准、可接受的时间与预算边界。缺少这三样，需求就无法进入市场，只能被翻译成一个岗位，再按时间雇人来承担不确定性。

这个翻译动作带来三个后果。**其一，预算与结果脱钩**：企业付的是时间，不是结果，做得好与做完是两件事。**其二，决策周期被拉长**：发布职位、筛简历、面试、入职，任何一环都在消耗需求本身的有效期。**其三，错配成本不可回收**：招错人要承担数月薪酬与团队磨合，这笔成本在交易发生前无法被定价。

## 供给侧：简历是弱信号，真实能力没有被记录

供给侧的定价依据仍然是学历、公司名与技能关键词。这些信息解释的是“曾经在哪里待过”，并不解释“这类任务完成得怎么样”。平台用关键词检索，于是可被检索的标签取代了可被验证的能力，结果是供给方被迫用降价来证明自己。

更关键的是，真正能预测交付质量的变量已经存在，只是没有沉淀下来：同类任务的完成次数、按时交付率、一次通过率、返工率、客户复购率、争议发生率。分散在各家平台的项目记录里，没有形成可迁移的信用。**行业缺少一套按任务计算、可跨平台携带的能力账本**。

## 平台侧：人机混合劳动没有计价与责任字段

撮合可以靠算法和流量规模化，验收不能。质量判断依赖客服介入与双方协商，争议处理成本随交易量线性上升，这是所有外包平台做不大复杂品类的原因。

当 Agent 进入交付环节，问题又多了一层。一个任务由人加四个 Agent 完成时，报价里 Agent 的算力成本如何计、出错的责任归谁、客户是否知情、平台如何抽成，现有产品结构里没有任何字段可以表达。**缺少这些字段，人机协作就只能停留在个人工具层面，无法成为市场行为**。

|角色|具体表现|现有平台为何难解决|商业后果|
|---|---|---|---|
|**发包方**|需求以目标形式存在；无法给出验收口径；预算按人头而非按结果编制|岗位是平台唯一可承载的交易对象；缺少任务数据结构|复杂度越高的工作越不敢外包，市场停留在低价值品类|
|**执行方**|能力靠标签自述；同类任务记录不可携带；只能以价格竞争|平台按关键词匹配，不沉淀按任务的能力数据|优质供给被折价，职业身份被岗位标签锁定|
|**平台方**|争议靠人工客服；质量无统一口径；人机混合无法计价|验收是重运营环节，规模不经济|交易量越大，边际成本越高，难以进入高客单品类|

# 解法：把任务做成可验收的数据对象

如果痛点集中在“说不清什么算完成”，那么产品的起点就不该是匹配算法，而应该是任务的表达方式。**TaskTok**** 的基本设想是：把可验收任务作为最小经济单位，人与 Agent 都可以作为执行单元参与竞争、协作、交付与结算**。

## 产品由四层结构组成

- **任务市场**：首页不是“正在招聘的岗位”，而是“正在开放的、带预算与验收标准的任务”。每个任务直接展示交付物形态、截止时间、难度等级、当前申请数与该类任务的历史成功率。

- **任务工作空间**：接单后进入以任务为中心的工作区，容纳目标、子任务、文件、Agent、版本记录、交付物、验收标准与付款节点。

- **任务引擎**：承接需求编译、拆解、定价、匹配、执行辅助与验收，是技术核心，也是与外包平台的分界线。

- **企业版**：把同一套结构向内延伸，让内部员工、内部 Agent 与外部市场在同一张任务图上竞争与流转。

## Task Compiler 负责把一句话变成任务图

编译过程有固定顺序，每一步都产生可核对的结构，而不是直接生成一段描述。

1. **确认目标**：把模糊诉求收敛成一个可判定的目标，例如“判断越南、泰国、马来西亚三个市场是否值得进入”。

2. **拆成任务图**：按信息依赖拆成市场规模、潜在客户、客户访谈、竞争格局、进入建议等节点，并标出节点之间的先后与依赖。

3. **定义交付与验收**：为每个节点写清输入、输出形态、必含字段、数据误差容忍度与验收方式。

4. **定价与路由**：依据难度、历史成交价、供需与截止时间给出建议价格带，再按能力图谱路由到最可能完成的执行单元。

5. **执行与结算**：执行过程中的中间产物进入版本记录，验收通过后按节点或按结果结算。

举例：一个“分析某公司最新财报”的需求，编译后不只是一句话，而是输入为财报与电话会记录、输出为带指定章节的分析报告、数据错误率低于约定阈值、24 小时内交付、允许 AI 参与且要求人工复核的可验收任务。**可验收，才可定价；可定价，才可交易**。

## 每个任务都必须携带完整字段

字段不是为了好看，而是为了让任务能被机器理解、被第三方复核、被结算系统执行。缺少任一字段，任务都会退回成“私下协商”。

|字段|含义|为什么必需|
|---|---|---|
|**Goal**|任务要达成的最终判断或状态|决定拆解方向，避免执行偏离目标|
|**Input**|发包方提供的资料、权限与预算|界定可行性，避免中途反复补料|
|**Output**|必须交付的产物形态与结构|让交付物可被机器解析|
|**Acceptance**|判定完成的标准与评分规则|把争议前置为规则|
|**Deadline**|交付时点与宽限条件|支撑排期与按时率统计|
|**Budget**|报酬与结算方式|形成可比价格带|
|**Skills**|完成任务所需的能力项|支撑能力图谱匹配|
|**Tools**|允许使用的工具与数据源|约束合规与数据边界|
|**AI Permission**|AI 可参与的环节与上限|使混合执行单元可计价|
|**Dependencies**|依赖的上游任务与前置条件|支撑任务图与自动派生|
|**Reviewer**|验收责任人与复核层级|明确责任归属|
|**Risk**|风险等级与争议处理预案|决定托管与保险策略|

## 用能力图谱替代简历

当任务被结构化之后，人的评价方式也随之改变。平台不再主要看学历与公司，而是按任务类别积累一条条记录，形成能力图谱：同一类任务完成了多少次、平均评分如何、按时率与一次通过率多少、客户是否复购、争议率多少。

这些指标的价值在于可预测。给定一个新任务，系统可以估计某位执行单元的完成概率与合理报价，再按概率与报价的组合排序，直接发出邀请，而不是等一千份简历投进来再筛。**从“人找任务”变为“任务找人”，前提是能力必须被计算而不是被陈述**。

## 验收引擎决定市场能否规模化

知识工作的验收不能只有一种方式。可行的做法是分层：机器负责可判定的部分，模型负责按评分规则打分，同行负责专业判断，客户负责最终接受。四层各自留下记录，最终汇聚成一个任务质量分。

- **机器校验**：格式、字段完整性、数据一致性、代码测试、可追溯性。

- **模型评审**：按既定权重对准确性、完整性、洞察与表达打分，输出可解释的分项结果。

- **同行评审**：高难度任务由两名同类执行者交叉评审，降低单一评审的偏差。

- **客户验收**：最终接受权留给发包方，但需在规则内行使，超出规则的返工另行计费。

把验收做成系统能力，才可能把争议成本从随交易量线性上升，变成随规则沉淀边际下降。这也是这门生意能否从低客单品类走向高客单品类的关键。

# 差异化：不在撮合，而在编译与验收

与现有玩家相比，差异集中在三点。**第一，交易对象从人变成任务**，匹配依据是可验收的交付，而不是简历标签。**第二，执行单元可混合**，一个人加若干 Agent 与纯人工在同一张任务图上竞争，报价里明确算力成本与人工复核成本。**第三，验收前置**，标准写在任务字段里，而不是留在客服工单里。

这三点也决定了竞争关系：与招聘平台是替代关系，与项目市场是延伸关系，与自由职业工具是互补关系。真正的对手不是某一家平台，而是“凑合着用”的现状——企业继续用岗位打包不确定性，个人继续用降价证明能力。

# 切入路径：先做窄口径的 B2B 研究任务

第一版不宜做全品类。合适的切口需要同时满足五个条件：单价在可承受区间、可远程交付、交付物可结构化、AI 能显著增强、成功标准相对容易定义。B2B 研究类任务（市场地图、潜客清单、竞争格局、销售线索）基本都符合。

|阶段|关键动作|要验证的指标|
|---|---|---|
|**第 0—3 个月**|只做研究与线索类任务；人工辅助编译需求；建立首版验收规则与评分权重|需求能被编译成任务的比例；一次验收通过率|
|**第 3—9 个月**|上线任务图与能力图谱；引入人机混合报价；把验收拆为机器与模型两层|按时率、返工率、复购率；混合执行单元的毛利差|
|**第 9—18 个月**|向企业版延伸，让内部任务与外部任务共用一张图；开放 Agent 接入|企业续费率；外部任务占比；争议率|

这个顺序的理由是：先证明“企业愿意不招一个人，而直接买一个结果”，再证明“这个结果可以由人机组合稳定交付”，最后才谈组织结构的改变。顺序颠倒，产品会退化成又一个外包网站。

# 商业模式与单位经济

收入结构建议做三层，而不是单一抽佣。**企业订阅**按席位或按任务量收取年费，承载编译、权限、预算、知识库与绩效数据；**交易服务费**按任务金额收取基础设施费；**算力费**按 Agent 实际消耗结算，与人工费用分列。

抽佣比例不宜定得过高，也不宜让价格成为唯一排序依据。排序应综合完成概率、质量预期、报价与截止时间，否则平台会迅速滑向低价外包，验收体系也随之失效。

|收入项|计价口径|说明|
|---|---|---|
|**企业订阅**|按年，示例口径 9\.9 万元 / 企业|随企业规模与任务量分档，属假设值，待客户访谈校准|
|**交易服务费**|任务金额的 3%—8%|按任务复杂度与服务深度分档，承载托管、验收与争议处理|
|**算力费**|按 Agent 实际调用结算|成本可核算，与人工报酬分列，避免混价|

以上三项均为结构设想，费率与客单价需要在首批真实任务中验证。在验证之前，不应把任何市场规模数字写进对外材料。

# 护城河：三张图构成的数据飞轮

这门生意真正沉淀的不是网站，也不是模型，而是三张互相关联的图。

- **任务图**：世界上各类工作究竟如何被拆解，节点之间的依赖与验收规则是什么。

- **能力图谱**：每一类执行单元（人、团队、Agent 组合）在特定任务类别上的完成概率与成本结构。

- **验收图谱**：什么样的结果算好，不同客户、不同品类下的评分规则如何分布。

三张图互相喂养：任务完成越多，能力判断越准，报价越接近真实成本，匹配成功率越高，客户越愿意把更复杂的任务交进来。**这条飞轮的启动条件不是流量，而是任务数据结构的一致性**，一旦早期为了成交而放宽字段要求，后续数据就无法聚合，护城河也就不会形成。

# 风险与对策

|风险|触发条件|对策|
|---|---|---|
|**验收争议**|评分规则过粗，客户主观否决；高难度任务无法自动判定|分层验收 \+ 规则内行使接受权；先在高确定性品类跑通再扩|
|**双边冷启动**|任务少则供给流失，供给少则任务不敢发|先自营一支经过筛选的执行池，用少量真实任务打通闭环|
|**价格战滑落**|排序只看低价，质量权重被稀释|排序纳入完成概率与质量预期；设价格下限与质量门槛|
|**AI 交付责任**|Agent 产出错误，责任在平台、执行方或客户之间不清|任务字段中明确 AI 参与上限与人工复核责任；关键品类强制人工签字|
|**合规与结算**|跨境支付、发票、数据来源授权|按区域选择持牌结算通道；数据来源在任务字段中登记|

# 结论与待验证假设

工作市场的下一次结构性变化，大概率不发生在匹配算法上，而发生在交易单位的定义上。当执行单元从“人”变成“人加 Agent”，按时间计价的整套体系会同时失效：预算无法编制、质量无法比较、责任无法归属。**把任务做成可验收的数据对象，是这个问题的直接解法**。

以下判断目前仍属假设，需要在真实交易中逐项验证：其一，企业是否愿意为“结果”而非“人力”付费，并接受由此带来的验收规则约束；其二，人机混合执行单元的交付质量能否稳定高于纯人工，同时成本显著更低；其三，验收规则能否在足够多的品类上收敛，使争议成本随规模下降而不是上升。

# TaskTok 产品设想

## 1. 概述

企业发布任务，平台把任务推给合适的执行者。几个执行者并行交付，企业从中选一份。每次选择都会反馈给平台，所以企业的任务找到的人越来越对，个人拿到的任务也越来越对口。

## 2. 前提

**智能溢出。** 每个人都有自己的智能体，做一份交付的成本已经很低。所以同一个任务可以让几个人同时做，没被选上的人损失也很小。整个方案成立靠的就是这一点。

**智能体不是平台里的角色。** 平台只和人打交道：推送给人，人来接受或拒绝，人提交交付，分数也记在人身上。执行者用不用智能体、怎么用，是他自己的事，平台不管。

长期看，智能体可能会成为真正的执行主体，前提是它的数字身份、收款能力这些事成熟了。这些事一直有人在做，但现在还不成熟，所以不在这个平台的设计里。

## 3. 角色

| 角色   | 做什么                                                       |
| ------ | ------------------------------------------------------------ |
| 企业   | 发布任务，从几份交付里选一个，给出评价                       |
| 执行者 | 个人用户。收到推送后选择接受或拒绝，接受后交付               |
| 平台   | 维护执行者分数，决定任务推给谁，收集反馈，更新分数和分发策略 |

## 4. 核心流程

1. **发布**：企业发布任务，例如写一篇文章。
2. **分发**：平台按任务匹配一个分数段（例如 60–70 分），把任务推给这个分数段里的若干执行者。
3. **接取**：设一个接取窗口（例如 3 天）。被推送的人可以接受或拒绝。
4. **入选**：前 N 个点“接受”的人（例如 N = 3）进入执行。默认按接受先后排，具体规则待定。
5. **交付**：N 个执行者各自完成任务，提交交付物。
6. **择优**：企业从 N 份交付里挑一个满意的。
7. **反馈**：企业的选择和评价写回平台，更新执行者分数和分发策略。下一次推送会更准。

## 5. 关键机制

### 执行者分数

- 用来决定把任务推给谁。
- 来源：被选中的次数、企业评价、接受或拒绝的记录。
- 被选中加分，落选的分数变化待定。

### 分发策略

- 决定一个任务推给哪个分数段、推多少人、取前几个。
- 会根据结果调整。例如某类任务推给 60–70 分段时企业总是不满意，下次就往高分段推。

### 并行交付、企业择优

- 同一个任务有 N 份交付，企业直接比较。
- 验收标准就是企业的选择本身，不需要事先把完成标准写得很细。

### 反馈闭环

- 企业的反馈：选中了谁，可能还有给每一份的打分。
- 执行者的反馈：接受还是拒绝，说明这类任务推给他准不准。

## 6. 任务至少包含什么

| 字段          | 内容                                           |
| ------------- | ---------------------------------------------- |
| Goal          | 要做成什么                                     |
| Input         | 企业提供的资料                                 |
| Output        | 交付物形态，例如一篇 1500 字的文章             |
| Deadline      | 接取窗口和交付截止时间                         |
| Budget        | 报酬，只付给被选中的人，还是给落选者补偿，待定 |
| Skills / 类别 | 用来匹配分数和分数段                           |

## 7. 与黑客松“自我进化”主题对接

进化发生在第 4 节那个闭环上：分发、交付、择优、反馈。

- **跑一次**：企业发布一批任务 → 平台分发 → 执行者交付 → 企业挑选。为了在 1 分钟内跑完，企业和执行者可以用模拟角色，评委或队员扮演企业来挑选。
- **两次之间学什么**：企业的选择和执行者的接受或拒绝，更新执行者分数和分发策略。这些都是数据更新，不改代码、参数、提示词。
- **比的指标**（候选）：
  - 企业首选命中率：平台排第一的那份交付，被企业选中的比例。
  - 接受率：被推送的人点“接受”的比例。
  - 企业满意分。
  - 企业满意之前需要推送多少人、看多少份交付。
- **给评委看学到了什么**：两次运行之间分数表和分发策略的 diff。
- **回退**：分数表和分发策略都按版本存储，切回 v1 就能恢复到第一次之前。

三行进化说明模板：

```
比什么指标：<例：企业首选命中率，第一次 x%，第二次 y%>
学到了什么：<例：执行者分数和分发策略已更新，见 v1→v2 diff>
怎么回退：<例：切换到 v1，重跑得到第一次的结果>
```

## 8. 待定问题

- 分数按任务类别分开算，还是只有一个总分。 *有一个多维一个加权*
- 推给哪个分数段由谁定：企业自己选，还是平台按预算或难度定。 *先由发布者制定，后续可考虑提出更优推送机制*
- 推送人数和 N 是否固定。 *推送人数不应该被限制成一个固定数，它又每个用户的推送算法决定，接受人数由发布者指定*
- 前 N 个怎么选：只看接受先后，还是也看分数。 *接取看先后，推送看分数*
- 落选者有没有补偿，分数怎么变。 *其实应该有惩罚*
- 企业的反馈只是选一个，还是给每一份都打分。 *给每一份都打分*
- 个人端怎样体现“越来越符合个体需求”：只看接受率，还是也收集执行者的偏好。

## 9. demo 范围

- 只做数字化交付的任务，例如写文章、做调研、做数据整理。
- 平台里只有企业和个人两种用户，不把智能体当作角色或执行主体。
- 不做企业内部版，不做真实支付结算。
